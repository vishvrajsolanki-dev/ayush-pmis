## Canonical Main SIH Demonstration Path

All steps run entirely on synthetic data generated by the Part 9 generator — **no external dependency required for the demo to run end-to-end.**

### Step 1 — Student Profile & Evidence
Show a student with self-reported and institution-verified evidence side by side, illustrating `verification_tier`. Label verified evidence precisely: "verified by institution account" — never a stronger claim.

### Step 2 — Opportunities
Show a company-posted role with clear eligibility requirements (feeding `E`) separated from graded compatibility requirements (feeding `F`).

### Step 3 — Eligibility
Show `E(c,i)` gating a clearly ineligible pair out, and an eligible one proceeding. Make the binary, exclusive nature of the gate visible.

### Step 4 — Fit
Show `F(c,i)` broken into its graded sub-factors (skill/semantic overlap, location/sector compatibility), explainably — not as an opaque single number.

### Step 5 — Opportunity-Side Signal
Show the priority-tier display (never "confidence"), with a visible `outcome_signal_source: ML | HEURISTIC_FALLBACK` indicator. If fallback is active, show it plainly — the honesty of this indicator is itself part of the demo's strength.

### Step 6 — Explainable Priority
Show `Priority = α·F + (1−α)·O` computed transparently for a specific candidate–opportunity pair, with the actual `α` value used.

### Step 7 — Candidate Preferences
Show a declared ranked list, unmodified by the system — demonstrate that an empty/incomplete list is accepted as valid input.

### Step 8 — DA Allocation
Run and show a live allocation, with the state machine (`DRAFT → PROPOSED → ...`) visibly progressing.

### Step 9 — Human Review
Show an admin reviewing a proposed run, and one override with its stored, mandatory reason — demonstrate that the override is a distinct, linked, accountable record, not a silent edit.

### Step 10 — Snapshot/Audit
Show the immutable snapshot and its hash, and a corresponding audit-log entry.

### Step 11 — Outcome
Show a generated `OFFER_EXTENDED` event, explicitly labeled synthetic — never presented as a prediction about a real employer.

### Step 12 — Feedback/Analytics
Show an institutional analytics aggregate (sample size ≥10) reflecting a prior cycle's outcomes feeding forward into future matching.

## Where the "Wow Factor" Comes From

The visible, inspectable chain from evidence → eligibility → fit → signal → priority → mechanism-grounded allocation → human governance → immutable audit trail — **not any single model's accuracy.** The demo should make the honesty of the system's claims (visible `HEURISTIC_FALLBACK` indicator, explicit "synthetic" labeling, no "confidence" language) a visible feature, not something hidden to look more impressive.

## Feasibility

Every step above runs entirely on synthetic data; no external dependency is required for the demo to run end-to-end.

## Recovery (Not in Core Demo Path)

Recovery is available on request but is not part of the core 12-step sequence (see ANCHOR_TRACEABILITY.md). If shown, it must be labeled a **locally stable heuristic**, never full-market-stable.

## Guardrails for Judge Q&A (see ANCHOR_STATE_MACHINES.md / Master Part 25 for the full non-claims list)

If asked whether the model predicts real hiring outcomes: **no** — it is trained and evaluated entirely on synthetic data; deployment validity is explicitly not assessed.

If asked whether tie-breaking is fair: it resolves ties deterministically; it does not claim to address distributional fairness.

If asked whether recovery/override results are as stable as the original DA output: no — both are explicitly weaker, separately-stated properties.

If asked whether `F` and `O` are independent: no independence claim is made — only computational non-dependency (one does not consume the other's output).
